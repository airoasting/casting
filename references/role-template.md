# 역할 프롬프트 6칸 표준 틀

> 50명 팀원과 팀장의 시스템 프롬프트가 모두 따르는 틀이다. 역할을 새로 만들거나 고칠 때 본다.
> 이 파일은 손으로 쓴다(`sync_refs.py`가 생성하지 않는다). 정본 프롬프트는 `docs/assets/prompts.js`에 있다.

## 왜 6칸인가

역할 프롬프트 하나는 두 장면에서 쓰인다.

- **대화**: 사람이 사이트에서 복사해 대화의 시스템 프롬프트로 붙여 혼자 쓴다.
- **팀 실행**: casting 스킬 안에서 팀장이 서브에이전트로 띄워 팀원으로 쓴다. 이때는 되물을 수 없고, 팀장이 준 산출물 명세를 따른다.

예전 틀(핵심 역할, 도구, 워크플로우, 출력 형식, 예시, 품질 기준, 원칙)에는 문제가 세 가지 있었다.

- 실행 환경(Context)을 적을 칸이 없었다.
- 작법 조언과 금지선이 섞여 있었다.
- 출력 형식이 품질 기준과 떨어져 있었다.

그 결과 33명이 팀 안에서 "사용자에게 되묻는다"고 지시했고, 예시가 자기 금지선을 어겼다. 6칸은 이 문제를 칸 단위로 막는다. 칸 순서는 Role, Rubric, Workflow, Tools, Context, Guardrail이다. Rubric을 Workflow 앞에 두는 이유는 합격 기준을 일하기 전에 정하기 위해서다(SKILL.md의 산출물 명세와 같은 원리).

## 칸별 필수 항목과 10점 기준

| 칸 | 필수 항목 | 10점 기준 |
|---|---|---|
| **Role · 역할** | 정체성 한 문장, `맡는 일`, `맡지 않는 일`, `끝의 기준`, `판단 기준` | 맡지 않는 일은 인접 역할을 "직책(번호)"로 짚는다. 판단 기준은 이 역할에만 해당하는 판단 원리다(끝의 기준과 같은 말 금지) |
| **Rubric · 합격 기준** | 합격선 줄, 문체 줄, `출력 형식`, `점검 질문`, `점수 기준`, `예시`, `자기평가` | 질문 4~7개가 모두 "(출력 N) …?" 꼴이고, 출력 항목마다 질문이 하나 이상 걸린다. 점수 기준은 8·9·9.5·10점이며 합니다체다. 9점은 빠진 요소를 이름으로 적고, 10점은 9.5점에 없는 관찰 가능한 요소를 적는다. 예시는 출력 형식을 그대로 따르고 자기 금지선을 어기지 않는다 |
| **Workflow · 작업 순서** | 단계 목록, 마지막 점검 단계, `넘기는 곳` | 모든 출력 항목을 만드는 단계가 있다. 넘기는 곳에는 팀 구성에서 바로 다음에 오는 역할이 모두 있다 |
| **Tools · 도구** | `라벨: 내용` 줄들, `도구가 없을 때` | 실제로 쓸 수 있는 도구만 적고 이 역할에서의 용도를 쓴다. 참고 링크는 "읽는 자료"로 도구와 구분한다. README "장착 도구"와 일치한다 |
| **Context · 맥락** | `받는 것`, `꼭 있어야 할 입력`, `빠졌을 때`, `독자와 쓰임`, 대화 줄, 팀 줄 | 받는 것에는 팀 구성에서 바로 앞에 오는 역할이 모두 있다. 빠졌을 때는 필수 입력 각각의 기본값을 다룬다 |
| **Guardrail · 금지선** | 역할 고유 줄 1~3개, 공통 줄 | 실제 위험만 막는다. 사실 왜곡, 법·규제, 개인정보, 권리 침해, 되돌릴 수 없는 행동, 자문 오인이 그 대상이다. 작법 조언은 Role이나 Rubric으로 보낸다 |

## 공통 문장

모든 프롬프트에 똑같이 들어가는 문장이다. 한 곳만 고치면 51개에 같이 반영되도록 생성 단계에서 붙인다.

- **Rubric 합격선**: 9.5점이 합격선이고, 내보내기 전에 스스로 채점한다.
- **문체**
  - 문장은 합니다체로, 표와 목록은 명사형 개조식으로 쓴다.
  - 번역투, 불필요한 피동, 과장 수식어, 긴 줄표를 쓰지 않는다.
  - 브랜드 톤이나 도착 언어의 관례가 주어지면 그것이 우선한다.
- **자기평가**
  - 사람과 대화할 때만 붙인다. 자기 채점이며 독립 검토가 아니다.
  - 팀 안에서는 붙이지 않는다.
- **점검 단계**
  - "아니오"인 질문의 항목부터 고치고, 고치기는 두 번까지만 한다.
  - 그래도 미달이면 부족한 점을 적는다. 대화에서는 자기평가 줄에, 팀에서는 팀장에게 돌려주는 답에 적는다.
- **대화 줄**: 빠진 필수 입력은 한 번에 모아 두 개까지만 묻는다. 나머지는 기본값으로 진행한다.
- **팀 줄**
  - 묻지 않는다.
  - 독자가 판단에 알아야 하는 전제는 산출물 맨 위 "전제:" 한 줄에 적는다. 그 밖의 가정은 팀장에게 돌려주는 답에만 적는다.
  - 산출물 명세가 우선하고, 점검 기준도 명세에 맞춰 읽는다.
  - 검토자로 배치되면 반환 형식을 따르고, 판정과 지시만 내며 고쳐 쓰지 않는다.
- **공통 금지선**: 지어내지 않는다. 표지는 다섯 가지만 쓴다.

## 표지 다섯 가지

| 표지 | 쓰는 자리 |
|---|---|
| `[확인 필요]` | 모르는 사실·값 |
| `추정` | 근거나 산식을 대고 추론한 값 |
| `가정` | 입력이 비어 세운 전제 |
| `미정` | 자료에서 아직 정하지 않은 결정·담당·기한 |
| `(제안)` | 팀이나 작성자가 정해 넣은 날짜·값 |

이 밖의 표지(자료 없음, 검증 필요, 추측, 확인 중 등)는 쓰지 않는다. 검사기가 막는다.

## 고치는 법

1. `docs/assets/prompts.js`의 해당 id 문자열을 고친다. `references/agent-prompts.md`는 직접 고치지 않는다.
2. `python3 scripts/sync_refs.py`로 references를 다시 만든다.
3. `python3 scripts/sync_refs.py --check`가 통과해야 한다. 검사기가 보는 것은 다음과 같다.
   - 6칸 순서와 필수 항목
   - 질문과 출력의 대응, 점수 기준의 줄 수와 문체
   - 표지
   - "직책(번호)" 표기의 정확성과 옛 역할 이름
   - 팀 구성의 앞·뒤 단계가 받는 것·넘기는 곳에 있는지
   - `---` 줄과 `python3` 표기
4. 검사기는 질적 결함을 못 잡는다. 예시의 모순, 경계 충돌, 판단 기준의 고유성이 그런 예다. 중요한 수정 뒤에는 만들지 않은 검토자에게 위 10점 기준으로 판정을 받는다.

역할을 새로 넣을 때는 위 순서에 앞서 두 가지를 먼저 한다.

- `docs/index.html`의 `A` 배열에 역할을 추가한다.
- 팀 구성(`docs/assets/router.js`)에서 쓰이면, 그 단계의 산출물을 출력 형식이 만들 수 있는지 확인한다.
